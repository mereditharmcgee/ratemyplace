Pattern 1 — getDB call (most common):
```typescript

const db = getDB((context.locals as any).runtime);

```

Pattern 2 — env var access (e.g., contact.ts, signup.ts, places/*):
```typescript

// AFTER
import { getEnv } from '../../lib/runtime';

```
Adjust the relative `../../lib/runtime` path for each file's depth. Examples:
- `src/pages/api/contact.ts` → `import { getEnv } from '../../lib/runtime';`
- `src/pages/api/auth/signin.ts` → `import { getEnv } from '../../../lib/runtime';`
- `src/pages/api/admin/buildings/[id]/enrich.ts` → `import { getEnv } from '../../../../../lib/runtime';`

Pattern 3 — defensive guard (middleware.ts only):
```typescript
// BEFORE (src/middleware.ts lines 11-16)
const runtime = (context.locals as any).runtime;
if (!runtime?.env?.DB) {
  return next();
}
const db = getDB(runtime);

// AFTER
if (!context.locals.runtime?.env?.DB) {
  return next();
}
const db = getDB(context);
```
The optional chain `context.locals.runtime?.env?.DB` is still permitted because at runtime the value can legitimately be undefined (local dev without Wrangler). The TypeScript declaration says it exists, but runtime can still produce undefined; optional chaining is the correct defensive pattern.
