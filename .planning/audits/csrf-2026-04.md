# CSRF Audit — April 2026

## Summary

The CSRF posture of ratemyplace.org is **sufficient; no token-based CSRF implementation is required.** Three interlocking defenses cover every request category: (1) `SameSite=Lax` on all session and OAuth state cookies prevents cross-site POST requests from carrying authentication credentials; (2) Cloudflare Turnstile verifies human intent on every public unauthenticated POST form; (3) Astro's `security.checkOrigin` middleware rejects cross-origin form-content-type POST requests at the framework level. The one structural gap — that `checkOrigin` does not apply to `application/json` requests — is explicitly covered by Turnstile, per-IP rate limiting, and a content-type guard on the one JSON-accepting public endpoint (`/api/disputes`). No token-based CSRF (double-submit cookie or synchronizer token) is implemented or required.

---

## Verdict

**Sufficient — no token-based CSRF implementation required.**

The combination of SameSite=Lax session cookies + Cloudflare Turnstile + Astro `security.checkOrigin` adequately covers all request categories. Each endpoint category has a documented primary defense. The only gap (JSON content-type bypasses `checkOrigin`) is closed by Turnstile + rate limit + content-type guard on the one affected endpoint.

---

## Defense Stack

Active CSRF controls in this codebase:

- **SameSite=Lax session cookie** (`src/middleware.ts:29` fresh-session path; `src/middleware.ts:40` blank/logout path) — Lax means the session cookie is NOT sent on cross-site non-navigation POST requests (i.e., a form submitted from `attacker.com` targeting `ratemyplace.org` arrives without the session cookie, so auth middleware rejects it). Lax (not Strict) is intentional — see OAuth callback section.
- **SameSite=Lax OAuth state cookie** (`src/pages/api/auth/google.ts:21`) — state cookie is readable only by the same origin; the OAuth callback validates the cookie value against the `state` query parameter, making CSRF against the OAuth flow impossible even if the attacker knows the URL structure.
- **Astro `security.checkOrigin` default** — `astro.config.mjs` uses `output: 'server'` and does NOT override `security.checkOrigin`, so it defaults to `true`. This activates `createOriginCheckMiddleware()` which rejects cross-origin form-content-type POST requests (see exact behavior below).
- **Cloudflare Turnstile** on all unauthenticated public POST forms: `/api/auth/signup`, `/api/auth/forgot-password`, `/api/contact`, `/api/disputes`, `/api/bug-reports`.
- **Phase 17 content-type guards** on public endpoints — rejects requests whose `Content-Type` does not match the expected format, closing a vector where an attacker could craft a request with an unexpected content-type to bypass `checkOrigin`.
- **Phase 17 per-IP rate limits** on every public POST and search endpoint — limits the practical impact of automated CSRF attempts.
- **Google OAuth redirect URI allowlist** — Google only redirects to URIs registered in the OAuth client configuration; an attacker cannot redirect the OAuth flow to an arbitrary URI.

The audit verified that no other cookies in the codebase are set with a weaker `SameSite` attribute. All cookies are either session cookies (SameSite=Lax, set in middleware.ts) or the OAuth state cookie (SameSite=Lax, set in google.ts).

## Astro checkOrigin — Exact Behavior (CRITICAL)

Source: `node_modules/astro/dist/core/app/middlewares.js` (read directly during research).

```
FORM_CONTENT_TYPES = [
  "application/x-www-form-urlencoded",
  "multipart/form-data",
  "text/plain"
]
SAFE_METHODS = ["GET", "HEAD", "OPTIONS"]

Logic:
  if method in SAFE_METHODS → pass (no origin check)
  if Content-Type is present:
    if Content-Type in FORM_CONTENT_TYPES AND origin is not same-origin → 403
    if Content-Type NOT in FORM_CONTENT_TYPES (e.g., application/json) → pass (NO origin check)
  if no Content-Type AND origin is not same-origin → 403
```

**Load-bearing finding: `checkOrigin` does NOT cover `application/json` POST requests.** When a request carries `Content-Type: application/json`, the origin check is bypassed entirely — the request proceeds regardless of the `Origin` header. This means any endpoint that accepts JSON cannot rely on `checkOrigin` as a CSRF defense. It must have an alternative control.

The `checkOrigin` default is enabled by the `security.checkOrigin: true` schema default (verified: `node_modules/astro/dist/core/config/schemas/base.js` line 48) combined with `output: 'server'` in `astro.config.mjs`.

## Per-Endpoint-Category Coverage

### 5.1 Authenticated POST Endpoints

**Endpoints:** `/api/reviews` (POST, PUT, DELETE), `/api/admin/*` (all verbs), `/api/profile/*`, `/api/notifications/*`, and any future endpoint that requires `context.locals.user`.

| Defense | Coverage | Notes |
|---------|----------|-------|
| SameSite=Lax session cookie | Primary | Cross-site POST arrives without the session cookie → auth middleware returns 401 |
| Astro checkOrigin | Secondary | Catches form-content-type cross-origin requests before auth middleware runs |
| Turnstile | Not applied | Would degrade UX for logged-in users; not needed because SameSite=Lax is the controlling factor |

**Why it's sufficient:** A cross-origin attacker page cannot read the session cookie value (HttpOnly), and SameSite=Lax prevents the cookie from being sent on cross-site POST form submissions. The attacker can construct the request but it arrives unauthenticated, so the auth check at the top of every endpoint rejects it with 401. No authenticated action can be forced.

**Lax vs. Strict:** SameSite=Strict would provide marginally stronger protection (blocks cookies even on top-level cross-site navigations) but breaks the Google OAuth callback: when Google redirects the browser back to `/api/auth/google/callback` after successful authentication, that is a cross-site top-level navigation — Strict would drop the session cookie and the callback would fail. Lax is correct for this application. See REQUIREMENTS.md Out of Scope.

---

### 5.2 Public (Unauthenticated) POST Endpoints

**Endpoints:** `/api/auth/signup`, `/api/auth/login`, `/api/auth/forgot-password`, `/api/auth/resend-verification`, `/api/contact`, `/api/disputes`, `/api/bug-reports`.

| Endpoint | Content-Type | checkOrigin applies? | Primary defense | Secondary defense | Sufficient? |
|----------|-------------|---------------------|-----------------|-------------------|-------------|
| `/api/auth/signup` | multipart/form-data | YES | Turnstile | checkOrigin + rate limit | Yes |
| `/api/auth/login` | multipart/form-data | YES | Password authentication | Rate limit | Yes — attacker cannot authenticate without credentials |
| `/api/auth/forgot-password` | multipart/form-data | YES | Turnstile | checkOrigin + rate limit | Yes |
| `/api/auth/resend-verification` | multipart/form-data | YES | Token-in-URL (subsequent verify step requires the token sent to email) | Rate limit | Yes |
| `/api/contact` | multipart/form-data | YES | Turnstile | checkOrigin + rate limit | Yes |
| `/api/disputes` | **application/json** | **NO** | Turnstile + content-type guard | Rate limit | Yes — see note |
| `/api/bug-reports` | multipart/form-data | YES | Turnstile | checkOrigin + rate limit | Yes |

**Critical note on `/api/disputes`:** This endpoint accepts `application/json`, which means Astro `checkOrigin` does NOT apply (see exact behavior section above). Its CSRF protection is:
1. **Turnstile** — proves human interaction; a CSRF attack cannot pass a Turnstile challenge automatically
2. **Phase 17 content-type guard** — the endpoint explicitly rejects requests with a content-type other than `application/json`, preventing an attacker from submitting a form-encoded request to bypass Turnstile validation
3. **Phase 17 per-IP rate limit** — limits automated CSRF attempt volume

This is covered, but not by `checkOrigin`. When adding a new `application/json`-accepting endpoint in the future, these three controls must be wired — do not assume `checkOrigin` covers it.

**Note on `/api/auth/login`:** No Turnstile on login. Cross-origin CSRF against a login endpoint is low-risk: an attacker can try to log the victim in as the attacker's account (login CSRF), but this app's threat model considers login CSRF acceptable at this scale. Rate limiting prevents brute force. If login CSRF becomes a concern, Turnstile can be added to login.

### 5.3 GET Endpoints

**Endpoints:** `/api/search`, `/api/search/autocomplete`, `/api/buildings/*` (GET), and any read-only endpoint.

CSRF is not a concern for GET endpoints. CSRF attacks require state-changing requests; GETs are read-only by HTTP convention and by this codebase's implementation (no GET endpoint mutates state). Documented here for completeness.

GET endpoints have other concerns (rate limiting, query length validation — handled in Phase 17) but CSRF is not one of them.

### 5.4 OAuth Callback

**Endpoint:** `/api/auth/google/callback`

| Defense | Coverage | Notes |
|---------|----------|-------|
| SameSite=Lax OAuth state cookie | Primary | State cookie set at `/api/auth/google.ts:21`; callback validates cookie value against `state` query param; mismatch → reject |
| Google redirect URI allowlist | Secondary | Google only redirects to URIs registered in the OAuth client config; attacker cannot redirect to an arbitrary URI |

**Why Lax works for OAuth:** When Google completes authentication and redirects the browser to `/api/auth/google/callback?code=...&state=...`, that is a top-level cross-site navigation. SameSite=Lax sends the cookie on top-level navigations (but not on form POST cross-site requests). So the state cookie is present when the callback runs, and validation succeeds. SameSite=Strict would drop the cookie on this redirect and break OAuth entirely.

**How the state validation works:** At `/api/auth/google.ts`, a `state` value is generated and stored in a `SameSite=Lax` cookie. At the callback, the `state` from the query parameter must match the cookie value. Since an attacker cannot read or set a cookie for `ratemyplace.org`, they cannot forge a valid `state` value. CSRF against the OAuth callback is not viable.

## Out of Scope

The following were explicitly evaluated and rejected:

- **Token-based CSRF (double-submit cookie, synchronizer token)** — the three-layer defense (SameSite=Lax + Turnstile + checkOrigin) is sufficient. Adding a CSRF token would increase bundle weight, add a cookie round-trip, and require server-side state or HMAC signing for no capability gain.
- **SameSite=Strict migration** — anti-feature. Strict breaks the Google OAuth callback (cross-site top-level redirect drops the cookie). Lax is the correct level for OAuth-enabled applications.
- **CSP / X-Frame-Options revisit** — separate security concern, already configured in `src/middleware.ts`. Not in scope for CSRF audit.
- **Astro 6 / `@astrojs/cloudflare` v13 upgrade** — its own milestone. If `checkOrigin` behavior changes in a major version, that triggers a re-audit (see Re-audit Triggers below).
