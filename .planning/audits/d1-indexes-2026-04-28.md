## Query 1 — Search results: buildings LEFT JOIN approved reviews

**Source:** `src/pages/api/search/results.ts:44-54`

**SQL:**
```sql
SELECT b.*, COUNT(r.id) as review_count, ROUND(AVG(r.overall_score), 1) as avg_overall, l.name as landlord_name

LEFT JOIN reviews r ON b.id = r.building_id AND r.status = 'approved'
LEFT JOIN landlords l ON b.landlord_id = l.id
```

**Decision:** Add `idx_reviews_building_status` ON reviews(building_id, status).

**Reasoning:** The planner currently uses `idx_reviews_status (status=?)` to satisfy the LEFT JOIN ON clause `r.building_id = b.id AND r.status = 'approved'`. This means it looks up all rows with `status = 'approved'` across the entire reviews table, then filters by `building_id` on the returned rows. With a composite `(building_id, status)` index, the planner can instead look up only reviews for the specific building AND with the approved status in a single index lookup — satisfying both predicates at once rather than filtering after the status-index scan.

This is the core SQLite one-index-per-table rule: the planner picks ONE index per table per query. The composite `(building_id, status)` satisfies both the join predicate (`r.building_id = b.id`) and the ON-clause filter (`r.status = 'approved'`) in one lookup, which is more selective than either single-column index alone. PERF-06 unconditionally requires this composite.

**Source:** `src/lib/rateLimit.ts:39-41`

```sql
FROM rate_limits
```

**Decision:** Skip `idx_rate_limits_key_created` — existing `idx_rate_limits_key` already covers the equality predicate.

**Reasoning:** The EXPLAIN output shows `SEARCH rate_limits USING INDEX idx_rate_limits_key (rate_key=?)`. The planner uses the existing single-column index to locate all rows for the given `rate_key`, then filters those results by `created_at > ?`. This is the correct skip case per the skip threshold rule: `SEARCH ... USING INDEX` = existing index sufficient.

The practical impact of the `created_at` filter after the key lookup is minimal: rate_limits rows have short TTLs (60-second windows), and a cleanup DELETE runs before every CHECK — meaning rows per `rate_key` are at most equal to the rate limit window (60 requests). Filtering 60 rows in memory is not a meaningful cost. No composite needed.

## Query 5 — PERF-07 filter query discovery (buildings.city, buildings.building_type)

**Discovery method:** `grep -rn 'city =\|building_type =' src/`

**Result (verbatim):**
```
/c/Users/mmcge/ratemyplace-boston/src/pages/api/admin/buildings/[id].ts:72:      updates.push('city = ?');
/c/Users/mmcge/ratemyplace-boston/src/pages/api/admin/buildings/[id].ts:92:      updates.push('building_type = ?');
```

**Analysis:** Both matches are `updates.push(...)` calls inside an admin PATCH endpoint's dynamic SQL builder. These are `UPDATE SET` assignments — they assign values to `city` and `building_type` columns on an existing row, not WHERE filters on a SELECT. `UPDATE SET city = ?` does not read via a btree index; it is a write operation that locates the row by primary key, then overwrites the column. An index on `city` or `building_type` would not be consulted for these operations and would provide zero benefit.

There are zero `SELECT ... WHERE city = ?` or `SELECT ... WHERE building_type = ?` queries anywhere in `src/`. No hot-path, no cold-path, no admin query — none.

**Decision:** Skip both `idx_buildings_city` and `idx_buildings_building_type` — PERF-07 not applicable. No SELECT WHERE filter queries exist on these columns in `src/`. Indexes created without a query to satisfy are pure overhead (marginal write amplification on INSERT/UPDATE with no read benefit).

**Future trigger:** If a city or building_type filter feature ships (e.g., a "filter by neighborhood type" or "filter by city" search facet), re-run this grep and add the indexes at that time. This is not "indexes are bad here" — it is "no query exists yet for these indexes to help."
