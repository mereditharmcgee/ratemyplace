<objective>
Add the cross-view data consistency E2E test to `e2e/critical-flows.spec.ts`. Submit a review against the seeded `building-e2e-01`, approve it via the admin UI, then assert the displayed `overall_score` matches across three distinct data sources: the search SQL aggregate (`/api/search/results`), the building detail page's live calculation (`/building/test-cross-view-consistency`), and the profile page's per-review stored value (`/profile`).

Purpose: Closes TEST-02 — the cross-view divergence gap. Each view computes the score via a different code path:
- Search: SQL `ROUND(AVG(r.overall_score), 1)` over approved reviews
- Building detail: `calculateBuildingAverages(reviews)` recency-weighted live calc (since `building_scores` has no row for `building-e2e-01`)
- Profile: per-review stored `r.overall_score` from the reviews table

Submitting one review in the current year collapses all three to the same value (recency weight = 1.0, single-row average = the value itself). Any divergence is a real bug.

Output: Second test in the same describe block as TEST-01, sharing the `cleanupPhase20Reviews` and `submitReviewAsAuthedUser` helpers introduced in Plan 20-01.
</objective>

- search: SQL `ROUND(AVG(overall_score), 1)` over 1 row = `ROUND(overall_score, 1)`

  // ─── TEST-02: Cross-view data consistency ──────────────────────────────
  test('cross-view consistency: overall_score matches across search, building detail, and profile', async ({
    authedPage,
    adminPage,
  }) => {
    test.setTimeout(60000);

    // 1. Submit a single review against the test building. All 27 score fields
    //    are rated 4 in the helper, so the stored overall_score is deterministic.
    //    Single review + current-year submission collapses all three view code paths
    //    to the same rounded value (see Plan must_haves for math).
    const reviewId = await submitReviewAsAuthedUser(authedPage, TEST_BUILDING_ID);

    // 2. Approve via the admin UI — this is the same flow exercised by TEST-01.
    //    Search and detail pages only show APPROVED reviews, so this step is
    //    required for the assertions below to find the row.
    await adminPage.goto('/admin/reviews?status=pending');
    await adminPage.waitForLoadState('networkidle');
    const reviewRow = adminPage.locator('.cursor-pointer', { hasText: TEST_BUILDING_ADDRESS });
    await expect(reviewRow).toBeVisible({ timeout: 10000 });
    await reviewRow.click();
    await reviewRow.locator('button', { hasText: 'Approve' }).click();
    await expect(reviewRow.locator('span.rounded-full')).toContainText('approved', { timeout: 10000 });

    // 3. View 1: Search API. ROUND(AVG(overall_score), 1) for one approved review.
    //    Use authedPage.request.get — no page navigation needed for JSON response.
    const searchRes = await authedPage.request.get(
      `/api/search/results?q=${encodeURIComponent(TEST_BUILDING_SLUG)}`
    );
    expect(searchRes.status(), 'Search API must return 200').toBe(200);
    const searchData = await searchRes.json();
    expect(
      searchData.results?.length,
      `Search must return building ${TEST_BUILDING_SLUG}`
    ).toBeGreaterThanOrEqual(1);
    // Find the row matching our test slug (search may return other matches if 'test'
    // appears in other building names; defensively filter).
    const searchRow = searchData.results.find(
      (r: any) => r.slug === TEST_BUILDING_SLUG
    );
    expect(searchRow, `Search results must include slug=${TEST_BUILDING_SLUG}`).toBeDefined();
    const searchScore: number = searchRow.avg_overall;
    expect(typeof searchScore, 'avg_overall must be a number').toBe('number');

    // 4. View 2: Building detail page. The detail page reads building_scores, falls
    //    back to calculateBuildingAverages(reviews) when no row exists — which is
    //    the path for building-e2e-01 (no pre-seeded building_scores row).
    await authedPage.goto(`/building/${TEST_BUILDING_SLUG}`);
    await authedPage.waitForLoadState('networkidle');
    const detailScoreText = await authedPage
      .locator('.text-4xl.font-bold.text-teal-600')
      .first()
      .textContent();
    expect(detailScoreText, 'Detail page must render score').toBeTruthy();
    const detailScore: number = parseFloat(detailScoreText!.trim());
    expect(Number.isFinite(detailScore), `Detail score must parse: "${detailScoreText}"`).toBe(true);

    // 5. View 3: Profile page (as the user who submitted). Profile lists per-review
    //    stored overall_score from the reviews table — different aggregation level
    //    than search/detail but identical value for a single review.
    await authedPage.goto('/profile');
    await authedPage.waitForLoadState('networkidle');
    // Wait for the review card containing the test address to render.
    const profileReviewCard = authedPage
      .locator('.bg-white.border.border-gray-200')
      .filter({ hasText: TEST_BUILDING_ADDRESS });
    await expect(profileReviewCard).toBeVisible({ timeout: 10000 });
    const profileScoreText = await profileReviewCard
      .locator('.font-medium.text-teal-700')
      .first()
      .textContent();
    expect(profileScoreText, 'Profile must render review score').toBeTruthy();
    const profileScore: number = parseFloat(profileScoreText!.trim());
    expect(
      Number.isFinite(profileScore),
      `Profile score must parse: "${profileScoreText}"`
    ).toBe(true);

    // 6. THE ASSERTION. Exact equality across all three views.
    //    Math justification: SQL ROUND(AVG(x), 1) on one row = JS Math.round(x*10)/10
    //    when x is itself the result of Math.round(...)/10 at submission time.
    //    Recency weight = 1.0 for current-year review, single-row average = x.
    //    Any failure here is a real divergence bug.
    expect(
      searchScore,
      `Search vs detail divergence: search=${searchScore}, detail=${detailScore}`
    ).toBe(detailScore);
    expect(
      detailScore,
      `Detail vs profile divergence: detail=${detailScore}, profile=${profileScore}`
    ).toBe(profileScore);

    // Defensive note: if floating-point precision ever flakes, replace the two
    // .toBe() above with .toBeCloseTo(value, 1) (1 decimal precision matches the

    // notes this as the fallback. Do NOT preemptively use toBeCloseTo — toBe
    // catches floating-point divergence which is the actual bug class TEST-02
    // exists to detect.
  });

Implementation notes:

1. **Why both `request.get` AND `page.goto`:** The search test uses `request.get` to read the JSON directly (per RESEARCH.md primary recommendation). Detail and profile use `page.goto` because they render through React islands and require DOM-based score extraction.

2. **Defensive `find` on search results:** A naive `searchData.results[0]` would break if the q-parameter ever returned multiple hits. The slug match guarantees we read the correct row.

3. **Score selector for detail page:** `.text-4xl.font-bold.text-teal-600` is the only score-display element in the building detail header (verified in `src/pages/building/[slug].astro`). `.first()` is defensive against future layout additions but should match exactly one element today.

4. **Profile score selector:** Scope to the review card by building address, then read `.font-medium.text-teal-700` — this is the per-review score badge inside `ReviewListItem.tsx`. Other `.font-medium.text-teal-700` elements may exist elsewhere on profile (saved buildings tab); the building-address scope eliminates those.
